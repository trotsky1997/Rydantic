# Local sample run — 2026-10-25

This is one cloud-host microbenchmark run, **not** a general performance ranking.
Pydantic is faster on the flat, nested and 100-item successful JSON fixtures in
this run. Other cases and the explicitly copy-inclusive secondary mode are shown
below rather than selecting only favorable results. No runtime optimization was
made to change the outcome.

This baseline reuses each fixed payload after warmup. Pydantic's documented
`cache_strings=True` (`all`) default is unchanged, so this is warmed repeated-string
traffic, **not** cold-cache or high-cardinality traffic. The cache's contribution
to the timing gap was not isolated. See [the methodology](../README.md#repeated-payloads-and-string-caching);
future cache-disabled/varied-input diagnostics must not replace these original
measurements. This clarification does not alter the measured source or raw data.

Reproduce using the commands in [the methodology](../README.md) at the measured
commit. Inspect raw samples, hashes, build artifact and execution order with:

```sh
gzip -dc benchmarks/pydantic/evidence/2026-10-25.json.gz > /tmp/benchmark.json
```

Numbers below are **batch-average nanoseconds per operation**, median and IQR.
They are not individual-request percentiles. Ratio is Rydantic median / Pydantic
median: above 1 means Rydantic took more time in this particular measurement.
Baselines are retained in raw data and not subtracted. No cross-case aggregate.
